# Pilot robustness pass, 2026-11-07

Working tree after release v10 (commit `2ef0b16`). Not committed, not deployed. Source of the items: valun-open
`spec/OPEN-QUESTIONS.md` (revision 3) and `docs/ADVERSARIAL-FINDINGS.md` (F4). Tests: `test/robustness.test.mjs`
(own tracker port 3082), plus the adversarial F4 test. Where the right behaviour was a judgment call, the conservative
option was chosen; it is stated in the line.

| Item | What changed | Compatibility | Test |
|---|---|---|---|
| OQ-6 withdraw while an acceptance waits for its owner | Still allowed. The acceptance's `state` becomes `void_withdrawn` (plus `voided_at`), its pending approvals `void_withdrawn`, the `withdrawn` event carries `acceptance_voided: true`; the proposer's `next_actions` during `accepted_awaiting_owner` is `["wait_for_owner_approval", "withdraw"]`. | New acceptance state value and one more `next_actions` entry for the proposer; clients show unknown values as text. | `OQ-6: withdrawing an offer whose acceptance waits for the acceptor's owner voids the acceptance and its approval` |
| OQ-7 unswept expired offers count against mandates | `exposure()` sweeps each deal it counts (offers, held counters and held acceptances past `offer_expires_at` expire there), and `position()` sweeps before counting. | None: only fewer false `mandate_exceeded` refusals and accurate counts. | `OQ-7: offers and held acceptances past offer_expires_at that nobody has read no longer count against mandates or positions` |
| OQ-8 agreed deals never end | New terminal status `expired_undelivered`: an `agreed` deal not delivered 7 days after `deliver_by` ends (event `expired_undelivered` by `valun`, with `deliver_by` and `grace_days`), releases exposure, is counted under `expired_or_withdrawn` and listed in `recent_closed`; `deliver` sweeps first, so a delivery after the grace period is `409 wrong_state`. Views of agreed deals show `delivery_grace_ends_at`. Delivered-but-unreviewed deals are left alone (no flag added). | New status value. Checked without editing: `hermes-plugin-valun/tools.py` and `valun-open/python/src/valun/agent.py` fall back to `whose_turn: "nobody: the deal is expired_undelivered"` and `what_happened: <status>`; `valun/sandbox.py` buyer loop keeps polling until its deadline and returns the status. Owner console labels it. | `OQ-8: an agreed deal not delivered within 7 days after deliver_by ends as expired_undelivered and releases exposure; delivered deals are left alone` |
| F4 / OQ-29 lowering `approve_above` and open offers | At acceptance, an offer its owner never approved whose price is above the proposer owner's `approve_above` as it is then waits for that owner: `accepted_awaiting_owner`, new approval kind `confirm_offer` (subject `accepted_offer`), event `held_for_proposer_owner`. Approve forms the deal (after the acceptor's owner too, if needed; both approvals exist at once); reject withdraws the offer (acceptance `void_withdrawn`). Owner-approved offers are not held again. On confirm, the acceptor's hard limits are re-checked (`409 acceptance_not_authorized`); an acceptor-owner rejection voids a pending confirmation (`void_acceptance_rejected`). Acceptance view: `held_for`. | Uses the existing status `accepted_awaiting_owner`. Risk: the plugin's and `valun` agent's text for that status says "it becomes binding when your owner approves it", which is wrong for the acceptor when only the proposer's owner holds it (they are not edited). New approval kind appears only to the proposer's owner. | `F4 fixed (was low): lowering approve_above does not hold offers that are already open` (adversarial, `{todo}` removed); `F4/OQ-29: an open offer accepted after its owner lowered approve_above waits for that owner; approve forms the deal, reject withdraws the offer` |
| OQ-12 template timestamp in the future | The template's timestamp is never after the server's clock (the rule `complete` and the Basis tracker apply: later than the pair's last note, not in the future). If the last note is ahead, the template waits up to 3 s for the clock; further ahead it is `409 note_timestamp_ahead` with `retry_after_ms`, `last_note_timestamp`. The template inside a `stale_note` error never waits. | New error code only where a future timestamp was returned before (which `complete` refused anyway). | `OQ-12: the credit-note template timestamp never exceeds the server clock, even when the pair's last note is ahead of it` |
| OQ-13 `mandate_version` on a no-op PUT | Only a real change bumps the version, `mandate_changed_by/at` and the audit; a no-op returns the mandate unchanged with `changed: false` (counterparty order and expiry spelling do not count as changes). A real change returns `changed: true`. | Additive field `changed`. | `OQ-13: mandate_version changes only when the mandate really changes` |
| OQ-20 owner limits labelled as agent-recorded | `PUT /limits` records who set each field (`agent_limits_recorded_by`, in `/me`, `/owner` and the PUT response); refusals add `recorded_by` and say "limit recorded by the owner (PUT /limits)" for owner-recorded values. `source` stays `agent_limits` (the limit set); older values count as agent-recorded. Either token can still clear such a limit (documented). | Additive fields; `source` values unchanged (existing tests and spec rely on them). | `OQ-20: limits an owner records through PUT /limits are labelled as recorded by the owner, not from the owner's instructions` |
| OQ-24 owner tokens cannot be rotated | `POST /pilot/v1/owner/rotate-token` (owner token): new token returned once, old one `401` at once, agent unaffected, audit `owner_token.rotated` (no token), `GET /owner` shows `owner_token_rotated_at`. Owner console: "New owner token…" button (confirm, shows the token once, switches the tab to it). Documented in PILOT-API.md. | New route only. | `OQ-24: an owner can rotate its owner token: the new one is shown once, the old one stops working, and the rotation is audited` |
| OQ-25 deal-id existence oracle | `propose` verifies the signature before looking up the deal id: a bad signature is `403 bad_signature` with the same message whether or not the id exists; a correctly signed reuse is still `409 duplicate`. | None for valid clients. | `OQ-25: a proposal with a bad signature is refused as a bad signature whether or not its deal id exists` |
| OQ-31 residual (signer outage on template/complete) | The note message is built through `Pilot.noteMessage`, which turns a signer outage into `503 signer_unavailable` ("nothing was recorded"), as `safeVerify` does; "signer: ..." refusals unchanged. If the helper fails only in the read-back re-check after the tracker accepted a note, the deal is `note_issued` with `reverify_skipped` (the tracker holds exactly the signature verified at completion) instead of staying `issuing_note`. | 503 instead of 502 for the same failures; additive `reverify_skipped`. | `OQ-31/OQ-35: a signer outage during the credit-note template or completion is 503 signer_unavailable; tracker failures are 502 tracker_unavailable` |
| OQ-35 every 502 says "internal error" | `BasisError` sets `name` and a `code` (`signer_unavailable`, `signer_error`, `tracker_unavailable`) and a fixed `publicMessage`. lib/http.mjs answers `503 signer_unavailable` / `502 tracker_unavailable` / `502 signer_error` with that message (pilot: `{error: code, message}`; demo `/api`: `{error: message, code}`); details stay in the log. The demo MCP shows the fixed message instead of the raw text. | Error bodies for these failures change from `{"error": "internal error"}` to named codes. | same test as OQ-31 |
| OQ-32 residual (reason length message) | Messages now state the limits enforced: "longer than 600 (dispute 1100) characters, counting leading and trailing whitespace (at most 500 / 1000 without it)". Limits unchanged. | Message text only. | `OQ-32: the reason length messages state the limits actually enforced` |
| OQ-33 residual (invisible characters) | Also refused in signed text, profile fields and reasons: U+00AD, Hangul fillers U+115F/U+1160/U+3164/U+FFA0, U+E0100-U+E01EF, and (conservative choice) any U+FE00-U+FE0F that does not directly follow an emoji character (so stray and repeated variation selectors). Tag characters stay refused except in exactly the three RGI subdivision flags (England, Scotland, Wales), which now work; a general "U+1F3F4 + tags + U+E007F" sequence stays refused because it could spell hidden text. Escapes are written as `\u` escapes. | Text that was accepted before and contains these characters is now `400 invalid_field` (rare in practice). The spec vectors `ok/arabic-mark-soft-hyphen`, `ok/variation-selectors`, `ok/hangul-filler`, `terms/unicode-allowed-invisible`, `decline/soft-hyphen`, `decline/variation-selectors` (and dispute twins) and the `subdivision-flag` cases need regenerating. | `OQ-33: soft hyphen, Hangul fillers, ideographic and stray variation selectors are refused; RGI subdivision flags and emoji presentation are allowed` |
