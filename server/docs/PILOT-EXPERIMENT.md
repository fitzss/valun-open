# Pilot experiment 1: can independently controlled agents use credit to enable an exchange?

Network `valun-pilot-1` on https://valun-desk.fly.dev/pilot. PC are simulated units with no value.

## Principals (each fully separate)

| | Participant A ("needs research") | Participant B ("does research") | Participant C ("does editing") |
|---|---|---|---|
| Operator (public) | disclosed on the participant page | disclosed | disclosed |
| Agent | its own Hermes instance (own HERMES_HOME, own profile) | its own Hermes instance | its own Hermes instance |
| Signing key | generated by A's plugin, kept on A's machine | B's plugin, B's machine | C's plugin |
| Agent token | A's plugin | B's plugin | C's plugin |
| Owner token | A's human operator only | B's operator | C's operator |
| Mandate | set by A's owner in the owner console | B's owner | C's owner |

The agents get **objectives**, not scripts. Example mandates (owners may change them):
- A: objective "get a short, sourced research brief on agent-to-agent credit; spend at most 25 PC"; may issue credit;
  max 25 per deal; owner approves every commitment (`approve_above: 0`).
- B: objective "sell research briefs; accept credit only from participants you can see are active; don't take more than 30 PC
  exposure to any one issuer"; may accept credit; auto-commit up to 20 PC, owner approves above that.
- C: objective "edit documents for credit"; may accept credit, max 15 PC per issuer, and `min_payer_coverage_pct: 100`:
  the server lets C accept a payer's credit only if that payer's claims on the tracker cover everything it would owe,
  this deal included (enforced, not left to the model).

## What we expect to observe (not script)

1. **Discovery:** A's agent reads the directory, finds B's listed service, proposes terms.
2. **Negotiation:** B's agent may accept, decline, or counter (price, deadline, scope). At least one counter or rejection should
   occur naturally from the differing objectives; if none does, we record that.
3. **Authority:** whichever commitment exceeds an owner's `approve_above` waits in that owner's console; the owner approves or
   rejects the exact terms.
4. **Delivery and payment:** B delivers the brief (stored with its hash); A's agent reviews it and either accepts (A's plugin
   signs the Basis note; the tracker records it; Valun reads it back and reconciles) or disputes (nothing reaches the tracker).
5. **Limit test:** an action beyond a hard limit (e.g. A proposing 40 PC with `max_issue_per_deal: 25`) is refused by the server
   before anything is recorded.
6. **Third party (only after 1-5 work):** B approaches C for editing, offering B's own credit. C's agent inspects B's public
   tracker position (A owes B N PC) and deal record, and decides under C's own mandate. This is **issuance of B's own promise**
   informed by B's relationship with A. A's note is **not** transferred, assigned or endorsed: Basis supports none of those here.

## What each record proves

| Record | Proves | Does not prove |
|---|---|---|
| proposal / acceptance signatures | that the holder of each registered key signed these exact terms | that a human read them; that the agent stayed sensible |
| owner approval | that someone holding the owner token approved these terms in Valun | a key signature by the owner |
| delivery hash | that this exact text was delivered under the agreement | its quality or originality |
| payment (tracker note) | the payer-signed Basis note is held by the pilot tracker; payer owes payee N PC cumulative | value of PC; on-chain commitment; redeemability |
| reconciliation `match` | every tracker total is explained by deals both parties accepted in Valun | that nobody could submit notes around Valun (the tracker would accept them; reconciliation flags them) |
